概念：大模型的上下文（LLM Context）

§ 1. 一句话定义

上下文（Context）是大模型一次推理时输入的全部 token 集合—— 包括系统提示、工具定义、对话历史、检索到的文档、工具调用结果、以及用户当前的提问。 上下文工程（Context Engineering）则是"为下一次推理精心挑选该往窗口里放什么"这件事。

§ 2. 学习目标

  • 能列出"上下文"由哪几类 token 组成。
  • 能解释为什么"上下文越多效果越好"是个危险假设（context rot）。
  • 区分 Prompt Engineering 和 Context Engineering。
  • 能识别 3 种典型的上下文管理策略：compaction / structured notes / sub-agents。

§ 3. 核心问题

  1. 为什么"上下文窗口变大"没有终结所有 LLM 工程问题？
  2. 模型的注意力到底是什么"预算"，为什么会用光？
  3. Prompt Engineering 已经够强了，为什么还要 Context Engineering？
  4. 面对一个几十轮的工具调用 Agent，常见的上下文管理手段有哪些？

§ 4. 个人理解（含类比）

上下文就像 Agent 的工作台桌面。桌面越大（窗口越大）不必然让你工作效率更高； 相反，桌面上堆满杂物，反而让你难以找到关键的那张纸。 Context Engineering 就是每天开工前把桌面整理干净， 只摆当前任务真正需要的：清单、当前文件、上一份笔记。

我自己的判断：在动手做 Agent 之前，先把"上下文设计"想清楚，往往比"模型升级"回报更大。 一个 200K 上下文窗口塞满信息的 Agent， 不如一个在合适的时机精准检索到关键信息的 16K Agent。 这一点也是 Andrej Karpathy 反复强调的："Context engineering is the delicate art and science of filling the context window with just the right information for the next step."

§ 5. 核心机制 / 组成

5.1 一次推理时上下文由什么组成？

组件典型内容由谁控制
系统提示（System prompt） 角色、行为边界、输出格式、工具用法 开发者
工具定义（Tools / MCP） 函数的 schema、外部服务接口 开发者
外部数据 / 检索结果 文档片段、知识库检索、长期记忆 应用代码按需注入
对话历史 用户/助手往来消息 框架
工具调用结果 API 返回、错误信息 框架
当前用户输入 用户刚发的消息 用户

5.2 为什么"上下文越多越好"是个陷阱（Context Rot）

Context rot：随着上下文 token 数增加， 模型从中准确检索和基于整段推理的能力会下降， 不是断崖式，而是渐进的"软退化"。 Chroma Research 在 18 个模型的 needle-in-a-haystack 测试中发现这是普遍现象。

三方面成因（架构层面的根因）：

  • O(n²) 注意力复杂度：每个 token 都要和其他 token 计算关联， token 越多每个 token 能获得的"注意力份额"越稀薄。
  • 训练分布偏短：模型训练语料里短序列更多、对长程依赖的"肌肉"较少。
  • 位置编码外推（position interpolation）的代价：为支持更长上下文， 模型用的位置编码会牺牲一部分位置精度。

§ 6. 一个具体应用场景

场景：长时运行的代码仓库分析 Agent（Anthropic Claude Code 用法）。

  1. 用户："帮我把 repo/checkout/ 下的支付流程画成时序图，列出所有边界 case。"
  2. Agent 多轮调用工具（grep / read_file / pytest）， 上下文不断膨胀，逐渐接近 200K 上限。
  3. 触发 Context Editing：自动清除过期的工具结果，只保留最近几次的关键观察。
  4. 同时 Agent 把"已分析的模块列表 / 已发现的边界 case"写到 NOTES.md， 上下文窗口里只剩指针。
  5. 接近窗口上限时触发 Compaction：把整个对话压缩成 2–3 段摘要， 主对话从压缩后的状态续接。
  6. 最后才向用户汇报时序图。

整个流程里，上下文工程贯穿始终。 它不是在某一步做的，而是每一轮推理前都要重新决定上下文该长什么样——这正是它和"写一个 prompt"的关键区别。

§ 7. 容易混淆的问题 / 使用边界

7.1 Prompt Engineering vs Context Engineering

Prompt EngineeringContext Engineering
焦点 如何写好指令/系统提示 如何挑选每次推理输入的全部 token
时机 开发时一次性设计 每次推理前都要重做
适合 单轮分类/生成任务 多轮 Agent / 长链路任务

7.2 "上下文窗口" vs "注意力预算"

窗口大 ≠ 注意力够。 上下文窗口是"最多能装多少 token"，是物理容量；注意力预算是"模型实际能稳定用上的 token 量"。 厂商标的 200K、1M 是前者；实际能用多少要看后者。 经验法：把"真正常用上下文"当成厂商公布的 30%–50% 来设计。

7.3 不要无脑全量塞上下文

  • "多塞点上下文模型表现就更好"已被验证为过度简化——参见 context rot。
  • "lost in the middle"：长上下文里中间部分最容易被忽略，开始和结尾保留最好。
  • 过长的 system prompt 会挤占有效推理所需的位置。

§ 8. 自测题（可自我判分）

Q1. 一次 LLM 推理的"上下文"具体包含哪些内容？请列出至少 4 类。

参考答案：系统提示、工具定义、外部检索数据、对话历史、工具调用结果、当前用户输入中至少 4 类。

Q2. 什么是"context rot"？它和上下文窗口大小是什么关系？

参考答案：Context rot 指的是随着上下文 token 数增加， 模型从中准确检索和推理的能力下降的现象。它不是因为窗口"装不下"，而是因为装得越多，模型对每条信息的注意力越稀薄。是软退化而非硬断崖。

Q3. 说出 Prompt Engineering 和 Context Engineering 的 3 个区别。

参考答案：① 焦点：单条指令 vs 全部 token；② 时机：开发时 vs 每次推理前；③ 粒度：一次成型 vs 迭代监管。

Q4. 长任务中三种典型的上下文管理策略是什么？请举例。

参考答案：① Compaction（压缩历史，如 Claude Code auto-compact）； ② Structured Notes（写到外部文件，如 NOTES.md）； ③ Sub-agents（子任务派给独立 Agent 只回摘要，如 Claude Research）。

Q5. 用一句 Karpathy 的话概括 Context Engineering。

参考答案： "Context engineering is the delicate art and science of filling the context window with just the right information for the next step." （中文意译：在每一步给上下文窗口填进恰到好处的信息——这件事既需要艺术也需要科学。）
