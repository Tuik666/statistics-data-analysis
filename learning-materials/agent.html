概念：Agent（智能体）

§ 1. 一句话定义

Agent（智能体）是以大语言模型（LLM）作为决策核心， 能感知环境信息、规划步骤、调用工具， 并根据结果循环迭代以达成用户目标的系统。它不是"一次调用 LLM 回答问题"那么简单， 而是一个长期循环运行的自治任务执行者。

§ 2. 学习目标

  • 能用一句话区分 Agent、工作流（Workflow）、聊天机器人（Chatbot）。
  • 能复述 Agent 的三大组件（Planning / Memory / Tool use）及其作用。
  • 理解 ReAct（推理 + 行动）循环的工作时序。
  • 能在产品评估中判断"这个场景该不该用 Agent"。

§ 3. 核心问题

  1. Agent 和 Workflow 的本质差异是什么？什么场景必须用 Agent？
  2. 为什么 Agent 需要 Memory？短期记忆和长期记忆各解决什么问题？
  3. Tool use 让 Agent 得到了什么，又引入了什么风险？
  4. Agent 的错误为什么会"复合放大"（compounding errors）？
  5. 评估 Agent 的产出和评估普通 LLM 的产出，有什么不一样？

§ 4. 个人理解（含类比）

把 Agent 想成一个新入职的、能干但需要辅导的同事： 你给一个目标（"帮我准备这次季度评审"），它会自己去找相关数据、调工具、查邮箱、组织 PPT， 但每一步都可能判断错，需要你设边界、给反馈、看过程日志。 Workflow 更像一份SOP（标准操作流程），每个步骤固定。 Agent 是能临场应变的版本，但代价是更大的不确定性和更高的成本。

我自己的判断：当下大多数 LLM 应用 80% 的场景用普通 prompt + RAG 就够了， 只有当任务的步骤数不确定、需要动态分支、或者工具调用链太复杂时， 才值得付出 Agent 的额外成本与不确定性。这也是 Anthropic 在 Building Effective Agents 中反复强调的原则："只在简单方案已不够时再加复杂度"。

§ 5. 核心机制 / 组成

5.1 三大组件

  • Planning（规划）：把复杂目标拆成可执行子步骤，并能在过程中反思修正。 典型技术：Chain-of-Thought、Tree of Thoughts、ReAct、Reflexion。
  • Memory（记忆）：短期记忆 = 当前上下文窗口里的对话与思考； 长期记忆 = 外部向量库/数据库。
  • Tool use（工具使用）：调用外部 API、代码执行、文件读写、搜索引擎等扩展模型能力。

5.3 工作流 vs Agent 的分叉点

Anthropic 把"用不用 Agent"画成了控制流由谁决定的二分： 工作流的路径是开发者代码预先定义的（确定性的）， Agent 的路径是 LLM 基于环境反馈自己决定的（动态的）。

§ 6. 一个具体应用场景

场景：SWE-bench 风格的代码修复 Agent（Anthropic 自家部署示例）。

  1. 用户输入："仓库里这个 issue 修了 build 失败，帮我修。"
  2. Agent Planning：读取 issue → 在代码库里搜索相关文件 → 列出修改计划。
  3. Agent 执行：调用 read_file 看文件、edit_file 改代码、run_tests 验证。
  4. 如果测试失败，进入 Reflexion（反思） 步骤：分析错误日志，重新规划修改。
  5. 循环直到测试通过或达到最大迭代次数。

这个场景的关键不是"它很强"，而是"每一步都有可验证的反馈" —— 测试通过了代表改对了，没通过就需要反思。这正是 Agent 最能发挥价值的地方： 任务可验证、能拿到 ground truth、可能多轮迭代。

§ 7. 容易混淆的问题 / 使用边界

7.1 Agent vs Chatbot / LLM 应用

  • Chatbot：单轮或多轮对话，主要产出文本，一般不主动调用工具。
  • LLM 应用：可能在 prompt 中嵌入了工具调用，但通常是一次性调用，路径由开发者预设。
  • Agent：自主选择下一步，可能运行很多轮，能从环境反馈中恢复。

7.2 Agent vs Workflow（Anthropic 区分法）

  • Workflow：路径是代码预先固定（如提示链、编排者-工作者）。
  • Agent：路径是LLM 动态决定。
  • 判断开关："你能不能描述出全部步骤？"——能则 Workflow；不能则可能需要 Agent。

7.3 何时不要用 Agent

不要因为"Agent 火"就用 Agent。 决策拒绝 Agent 的常见信号：单步能解决的简单任务、可枚举步骤的处理、 延迟或成本敏感（Agent 通常 token 消耗是单次调用的 5–15 倍）、 安全性关键且结果必须 100% 确定的场景。

§ 8. 自测题（可自我判分）

Q1. 请用一句话给出 Agent 的定义，并指出和 Workflow 最关键的一个区别。

参考答案：Agent 是在循环中自主选择下一步行动的 LLM 系统；与 Workflow 的关键区别在于路径由谁决定——Workflow 由代码预定义，Agent 由模型根据环境反馈动态决定。

Q2. ReAct 循环的三个标准步骤分别是什么？为什么要循环？

参考答案：Thought（推理）→ Action（行动）→ Observation（观察）。 循环是因为：单步答案经常不够完成复杂任务，每一步都可能错，需要从观察里修正。

Q3. 为什么 Agent 的错误会"compound"（复合放大）？

参考答案：因为每一步的输出都成为下一步的输入；如果第二步的假设错了， 后续所有步骤都会站在错的前提上推理，造成错误层层叠加。 因此常配合 Reflexion / Evaluator-Optimizer 来中途纠偏。

Q4. 给出 2 个适合 Agent 的场景和 2 个不适合 Agent 的场景。

参考答案：适合：① 能跑测试自动反馈的代码 Agent；② 跨多个数据源、需要动态分支的研究类任务。 不适合：① 单步就能完成的摘要；② 输出必须确定、延迟敏感的生产关键路径。

Q5. "短期记忆"和"长期记忆"分别是什么机制？短期记忆的极限来自哪里？

参考答案：短期记忆 = LLM 当前上下文窗口里的对话/思考（In-context learning）； 长期记忆 = 外部向量库/数据库 + 检索。 短期记忆的极限来自上下文窗口有限 + 注意力预算有限（详细内容参见姊妹篇《LLM Context》）。
