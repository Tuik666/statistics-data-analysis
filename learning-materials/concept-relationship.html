三个概念是怎么相互作用的

Agent、LLM Context、Skill 三个概念常被混在一起讲， 但它们其实是不同层次的东西。这里给出它们之间的关系结构， 重点解释上下文如何影响 Agent 的工作， 以及Skill 如何沉淀可复用的任务知识。

§ 1. 一句话比喻

Agent 是一位长跑选手；
Context 是它随身携带的工作台，决定了它当前能看到、能想起、能用上的全部信息；
Skill 是贴在工作台上、随时可打开的操作手册合集， 让选手不必每次从零摸索。

§ 3. 上下文如何影响 Agent 的工作（重点）

这是我认为最重要的关系：上下文是 Agent 的工作状态，它的内容直接决定 Agent 这一刻能不能做出正确判断。

3.1 影响面 1：决策质量

  • 放进上下文里的关键信息，Agent 可能用到；
  • 没放进上下文，再重要的信息也"不在现场"——Agent 只能猜；
  • 放进错误的上下文，Agent 会基于错误前提推理（garbage in, garbage out）。

3.2 影响面 2：能记住多远

  • 上下文窗口外的历史，对 Agent 来说等于不存在。
  • 连续多轮工具调用后，上下文会越来越长，触发 context rot，质量下降。
  • 这就是为什么长时运行的 Agent 必须配合 compaction / structured notes / sub-agents 三件套。

3.3 影响面 3：工具与能力

  • Agent 能调用的工具（tool descriptions + MCP）本身也消耗上下文 token。
  • 工具描述写得太啰嗦，会挤压有效推理空间。
  • 结论："好工具"既要够清晰让 Agent 会用，也要够简洁别占地盘。

3.4 影响面 4：稳定性与可复现

  • 同一段 prompt 放在不同上下文里，输出可能差很大。
  • 想复现 Agent 的行为，不能只固定 prompt，还要固定"上下文配方"（注入了哪些检索、什么工具历史）——这就是评测工作的挑战。

§ 4. Skill 如何沉淀可复用的任务知识

4.1 沉淀什么

  • 可复用的指令：团队风格、领域规范、固定的工作流。
  • 工具用法说明："在这种 MCP 上该怎么调、常见错误码含义"。
  • 领域知识：行业术语、内部代号、最佳实践。
  • 自检清单："输出前自检这些项"的标准化流程。

4.2 怎么不撑爆上下文

  • 三级渐进式披露：YAML metadata（始终可见且便宜）→ SKILL.md body（相关时才加载）→ 链接文件（用不到绝不加载）。
  • Skill 互相组合：每个 Skill 保持单一职责，多 Skill 并存，不堆在一个 mega-Skill 里。
  • Skill 可执行脚本可被 Agent bash 调用，不必把实现读进上下文。

4.3 与 CLAUDE.md / Rules 的分工

  • "每次会话都该遵守" → CLAUDE.md / Rules（always-on）。
  • "只在某个场景下调用" → Skill（on-demand）。
  • "需要执行复杂流程" → Skill + scripts。

§ 6. 它们在一起时，一条请求的工作链路

  1. 用户输入到达 Agent 框架。
  2. 框架拼装本次推理的上下文：系统提示 + 工具定义 + 检索结果 + 历史 + 当前消息。
  3. System prompt 包含已装 Skill 的 metadata，Agent 据此判断哪些 Skill 相关。
  4. 若相关，用文件读取工具把对应 Skill 的 SKILL.md 装进上下文。
  5. 模型基于这份上下文推理出下一步动作。
  6. 如果动作是调用工具，得到结果，再次进入第 2 步循环。
  7. 逼近上下文上限时，框架可能触发 compaction / 写 NOTES.md / 把子任务交给 Subagent。

可以看到：每一轮推理都要重新决定上下文的形状， 而 Skill 是可以在合适时机被自动塞进工作台的工作手册。 这正是 Context Engineering 与 Skill 设计互相成就的过程。

§ 7. 学习路径建议

  1. 先看 Agent，理解整体形态与循环。
  2. 再看 大模型的上下文，理解每一次决策能看到什么。
  3. 最后看 Skill，理解如何把经验沉淀成可复用的资产。
