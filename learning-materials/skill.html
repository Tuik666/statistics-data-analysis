概念：Skill（Anthropic 风格的 Agent Skill）

§ 1. 一句话定义

Skill（技能）是一个由指令、脚本、参考文档组成的目录， 通过 YAML 元数据被 Agent 索引、按需加载进上下文， 让通用 Agent 拥有可复用的领域知识和工作流。 最简形式：my-skill/SKILL.md，复杂形式可加 scripts/、references/、assets/。

§ 2. 学习目标

  • 能描述 Skill 的最小结构和可选项。
  • 理解"三级渐进式披露（Progressive Disclosure）"的机制。
  • 区分 Skill 与三种相似概念：Subagent、CLAUDE.md / Rules、Plugin。
  • 能在自己的项目里决定一条知识该放 Skill 还是其它地方。

§ 3. 核心问题

  1. 为什么不让 Agent 一次加载全部知识？Skill 是怎么做到"按需加载"的？
  2. Skill 的最小可行版本是什么？复杂 Skill 的边界在哪里？
  3. Skill 与 Subagent、CLAUDE.md、Plugin 各自擅长什么？什么时候用哪个？
  4. Skill 的"描述"决定了什么？写一个含糊的描述会怎样？
  5. 如何把团队约定、领域知识、个人偏好放进 Skill，而不是堆在 prompt 里？

§ 4. 个人理解（含类比）

Skill 像一位随叫随到的领域顾问：日常坐着不打扰（不进入默认上下文）， 只在某个用例被触发时带着工牌（YAML 描述）推门进入工作间（上下文）。 进来的程度也分轻重——只带目录纲要（metadata）、带完整手册（SKILL.md）、 或带具体附录（linked files）。这种"分级别按需加载"，正是 Skill 能避免撑爆上下文的根本原因。

我自己的判断：在本仓库自带的 concept-learning-material-generator 项目级 Skill 里，我刻意保持 SKILL.md 不超过一屏阅读量。 一切经验证明：试图用一个超大 SKILL.md 兜所有场景，反而失灵——因为 Agent 倾向于只读取前 50 行就开干。 把复杂 Skill 拆成主文件 + references/，由模型决定是否深入，是更可靠的工程实践。

§ 5. 核心机制 / 组成

5.1 Skill 的目录结构

my-skill/
├── SKILL.md          (必填，YAML frontmatter + 正文)
├── scripts/          (可选；Python/Bash 等脚本，Agent 在需要时执行)
├── references/       (可选；按需进一步阅读的参考文档)
└── assets/           (可选；模板、字体、图片等)

5.2 三级渐进式披露

5.3 SKILL.md 的最小 YAML

---
name: my-skill
description: 简明扼要说明此 Skill 何时被调用、用一句话告诉 Agent 在什么场景下该启用它。
---

# my-skill

## 适用场景
...

## 输入信息
...

## 生成步骤
...

最关键的字段是 description—— 它决定是否被 Agent 选用，含糊的描述意味着 Agent 永远不会主动召它。

§ 6. 一个具体应用场景

场景：Anthropic 自家的 PDF 技能（来自其官方 blog 与 documentation）。

  1. 用户提问："帮我把这份 PDF 里第 3 页的表格填好。"
  2. Agent 看到系统提示里 PDF Skill 的 YAML 描述，判定相关。
  3. Agent 用文件读取工具把 pdf/SKILL.md 整段加载到上下文——这是第二级披露。
  4. SKILL.md 指引说"如果要填表，再去读 forms.md"——于是 Agent 再加载 forms.md，这是第三级披露。
  5. Agent bash 执行 Skill 自带的 scripts/fill_form.py 完成填表。
  6. 返回值直接回到对话。

关键观察：第二步里如果 Agent 没把 PDF Skill 的全部 SKILL.md 加载完，填表就会出问题； 但如果默认一次性加载全部 scripts/references/assets，token 又会爆炸。 三级披露在可用 token 与行为可靠性 之间做了工程上的平衡。

§ 7. 容易混淆的问题 / 使用边界

7.1 Skill vs Subagent vs CLAUDE.md vs Plugin

是什么加载时机典型用途
Skill 可复用指令/工作流/参考资料 相关时按需加载 风格指南、API 文档、复杂 SOP
CLAUDE.md / Rules 每会话自动加载的项目规约 每次启动固定注入 "用 pnpm 不用 npm"这种 always-on 规则
Subagent 独立上下文的隔离执行单元 被主 Agent 显式调用 读很多文件后只回摘要的研究子任务
Plugin 打包一组 Skill/Subagent/MCP 的发行单元 用户/团队级别安装 把整套规范一次性分发给团队成员
决策原则：该条规则永远要遵守→ CLAUDE.md； 某些场景下才用得上→ Skill； 需要隔离的上下文或并行 → Subagent； 要整体打包分发 → Plugin。 不要把"always-on"塞到 Skill 里（既浪费 token，又不会被严格执行）。

7.2 Skill 写不好的常见问题

  • description 太模糊："用来帮助处理一些文档" → Agent 不知道何时调用。
  • SKILL.md 巨长：2000 行指令没人读得完。
  • 用了专有内部术语没解释："按 cgl 流程走"——Agent 完全不懂。
  • 没声明自检清单：输出无标准化、Agent 自我评估失败。

§ 8. 自测题（可自我判分）

Q1. Skill 的最小结构是什么？可选目录有哪些？

参考答案：最小结构 = SKILL.md（含 YAML 元数据 + 正文）。 可选目录：scripts/（可执行脚本）、references/（按需读取的子文档）、assets/（模板/字体/图片）。

Q2. 三级渐进式披露分别指什么？为什么不能一次全加载？

参考答案：① YAML metadata（始终在系统提示）→ ② SKILL.md body（相关时被读入）→ ③ Linked files（按需进一步读取）。 一次全加载会占用大量 token，导致"context rot"，让其他任务的有效信号被稀释。

Q3. Skill 跟 CLAUDE.md 哪个该用来存"提交前必须跑测试"这条规则？

参考答案：用 CLAUDE.md（或 .claude/rules/）。原因是这条规则是每次会话都要遵守，属于 always-on 规则；如果做成 Skill，Agent 可能不会主动装载，会失效。

Q4. Skill 跟 Subagent 的本质区别是什么？各举一个典型用途。

参考答案：Skill 是被加载的知识，Subagent 是独立工作的工人（自带隔离上下文）。 Skill 典型用途：API 风格指南；Subagent 典型用途：读 50 个文件后只回摘要的研究任务。

Q5. 写 Skill 的 description 时最容易犯的错误是什么？

参考答案：写得太模糊、缺乏触发条件。比如"用来处理文档"没有任何触发信号。 好的 description 应包含何时调用（trigger）、做什么（action）和为什么（rationale）。
